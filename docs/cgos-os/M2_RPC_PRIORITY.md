# M2 lease RPC priority

Task 5A trace (Actions run 43782997295, artifact 14189227031) showed a 42.51 s graph with 2.43 s of worker child execution. After queued admissions the same peer started capability probes before scheduling task status. The peer had exactly one pending future, so a routine probe could consume most of a 3 s RPC budget and prevent a task call from starting. Task 5A also recorded a failed task status call and two failed initial/periodic probes. That trace does not establish the cause of the earlier final-stage timeout or isolate TCG's share of SSH round-trip time.

The coordinator now harvests replies, runs graph reconciliation and placement, then offers idle peers a capability probe. An online peer with an assigned lease uses that slot for lease traffic. A verified response to that lease is also liveness evidence: worker v2 checks the lease against its present boot identity before issuing a response. Transport failures and invalid responses do not extend liveness. Idle probing retains the 2 s cadence, and an offline peer must re-probe before accepting work. The 9.5 s freshness limit, 3 s RPC, 15 s lease, and 60 s reference graph deadline are unchanged. An already-started probe is allowed to finish within its original RPC bound; it is not overlapped or preempted. Capability refresh resumes when the lease and pending work clear. The single pending future and single reply slot remain bounded. No new SQLite writer, SSH session reuse, authorization changes, or local-mode changes were introduced.

The Task 5B workflow runs Linux regression tests before building the separate ISO, then verifies that exact image and runs the same single-graph Task 5A harness. It does not run acceptance or change the accepted M1 or previous M2 artifacts.
